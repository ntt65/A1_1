# 미션·평가 문서 괴리 해결법

미션 문서와 평가 문서를 함께 보면 정리가 안 되고 설명하기도 어려운 이유를 진단하고, 해결 순서를 정리한다. 진단 기준일은 2026-11-24이며, 대상은 [미션 문서](a1_1_mission.md), [평가 원문](a1_1_eval.md), [평가 Q&A](a1_1_evaluation_qa.md), [README](../README.md)다.

## 요약

- 두 문서는 서로 다른 문서가 아니다. 평가 원문은 **미션 원문 두 벌 + 평가문항 19개**로 되어 있다.
- 미션은 "무엇을 만들어라", 평가는 "왜 그렇게 했고 확장하면 어떻게 하겠느냐"를 묻는다. 같은 주제가 두 문서에서 다른 순서로 흩어진다.
- 문서마다 번호 체계가 다르고 서로 대응시킨 표가 없다.
- 같은 수치가 여러 파일에 반복돼 한 곳을 고치면 나머지가 어긋난다.
- 해결의 중심은 **평가 19문항을 행으로 하는 대응표 하나**를 기준으로 삼고, **설명은 평가 순서로** 하는 것이다.

## 원인 1. 평가 원문 안에 미션이 두 번 들어 있다

[a1_1_eval.md](a1_1_eval.md)는 413줄이다.

| 줄 | 내용 |
| --- | --- |
| 1~27 | 학습단계·학습주제 소개 |
| 28~199 | 미션 원문 전체 |
| 205~376 | 미션 원문 전체 (28~199와 완전히 같음) |
| 377~382 | 평가자료 (프로젝트 URL·브랜치) |
| 383~413 | **평가문항 19개 + 보너스** |

평가 원문에서 새로운 내용은 마지막 평가문항 부분뿐이다. 학습 사이트 페이지를 복사하면서 미션이 두 번 붙은 것으로 보인다.

함께 발견한 차이:

- 평가 원문의 미션 소개는 "데이터 분석은 AI 모델링의 출발점이다… 에너지·헬스케어 분야로도 전이된다"는 문단으로 시작한다. 이 문단이 [미션 문서](a1_1_mission.md)에는 없다. 미션 문서가 원문보다 짧다.
- 평가자료의 프로젝트 URL은 이 저장소가 아니라 `giyeop-cody/codyssey-A1-1-mission`이다. 템플릿 예시로 보인다.

## 원인 2. 미션과 평가는 묻는 방식이 다르다

| 문서 | 성격 | 순서 |
| --- | --- | --- |
| 미션 | 구현 목록 ("무엇을 만들어라") | 기능 순서: 4-1 데이터 로드 → … → 4-7 RFM |
| 평가 항목 1 (8문항) | 미션 요구사항을 다시 묻는 체크 질문 | 미션과 비슷하지만 묶음이 다름 |
| 평가 항목 2·3 (8문항) | 설계 이유와 원리 ("왜") | 주제별 |
| 평가 항목 4 (3문항) | 미션에 없는 확장·캠페인·ML ("만약") | 주제별 |
| 평가 항목 5 | 보너스 | 미션 5장과 같음 |

그래서 한 주제가 두 문서에서 다른 위치에 흩어진다.

| 주제 | 미션 위치 | 평가 위치 |
| --- | --- | --- |
| OOP 클래스 | 4-2 | 1-1, 2-1, 2-3 |
| 이미지 피처·벡터화 | 4-3 | 1-4, 2-2, 3-4, 4-1 |
| IQR·결측 | 4-4 | 1-5, 3-1, 3-2 |
| 통계 | 4-5 | 1-7 |
| 시각화 | 4-6 | 1-5, 1-6 |
| RFM | 4-7 | 1-8, 3-3, 4-2 |
| 노트북 마크다운 | 2. 최종 결과물 | 2-4 |
| 확장·예측 | 없음 | 4-1, 4-3 |

미션 순서로 설명하면 평가 질문이 여기저기서 튀어나온다. 평가 순서로 설명하면 같은 코드를 서너 번 다시 연다. 어느 한 순서로 정리해도 다른 쪽은 흩어지는 구조다.

## 원인 3. 번호 체계가 여러 개이고 대응표가 없다

| 문서 | 번호 체계 |
| --- | --- |
| 미션 문서 | `4-1`~`4-7`, `5-1`~`5-3`. 원문에도 "9. Test Case" 아래 "8. 결과 예시"처럼 번호가 꼬여 있음 |
| 평가 원문 | "1. 미션 소개"가 두 번, "3. 미션 소개", "5. 평가문항" / 항목 1~5 |
| 평가 Q&A | `1-1`~`4-3` |
| 체크표 | `#1`~`#19` (평가 피드백 대응 번호) |
| 상세 계획 | `Q11`, `R2`, `C1~C5` 등 |
| 발표자료 | "필수 19문항" |

같은 요구사항을 가리키는 번호가 문서마다 다르고, 이 번호들을 서로 연결한 표가 없다.

## 원인 4. 같은 수치가 여러 파일에 반복된다

2026-11-24 기준 개수:

| 수치 | 들어 있는 파일 수 |
| --- | --- |
| "212" (IQR 상한 초과 행) | 9개 (README, 체크표, 상세 계획, 평가 Q&A, 미션 문서, README 학습 문서, 네이토 평가 결과 2개, tech_study) |
| "VIP 270명" | 4개 |

README 개편(#32)에서 오래된 수치(12셀, 테스트 20개, 5대 세그먼트)가 발견된 원인이 이것이다.

## 해결 방법

### 1단계. 평가 원문 정리

- 원본은 [평가 PDF](a1_1_eval.pdf)로 보존한다. md는 "PDF에서 옮긴 정리본"이라고 머리말에 적는다.
- md에서 중복된 미션 사본(205~376줄)을 빼고, 첫 번째 사본에도 "미션 원문은 [미션 문서](a1_1_mission.md) 참고"만 남기는 방안을 검토한다.
- 평가 원문에만 있는 미션 소개 첫 문단을 미션 문서로 옮긴다.
- 프로젝트 URL이 템플릿 값이라는 점을 주석으로 남긴다. 원문 값은 바꾸지 않는다.

### 3단계. 설명 순서를 평가 순서로 통일

- 평가자는 평가문항으로 묻는다. 설명 자료(평가 Q&A, 평가 발표자료)는 평가 순서를 따른다.
- 미션 문서는 "빠뜨린 요구사항이 없다"는 것을 확인하는 용도로만 쓴다. 설명 자료로 쓰지 않는다.
- 평가 항목 2~4의 주제가 겹치는 경우(예: RFM 1-8 → 3-3 → 4-2)는 처음 나올 때 코드를 보여주고, 이후에는 "앞에서 본 코드"로 이어 간다.

### 4단계. 수치는 한 곳에만 둔다

- 실행 결과 수치의 기준은 README 결과 절과 [`analysis_aggregates.json`](results/analysis_aggregates.json)이다.
- 평가 Q&A와 미션 문서부터 수치를 직접 쓰는 대신 README 결과 절을 링크하는 방향으로 줄인다. 설명에 꼭 필요한 대표 수치(212행, VIP 270명 등)만 남긴다.
- 평가 결과 기록(네이토 평가 문서)과 체크표의 수치는 그 시점의 기록이라 바꾸지 않는다.

## 하지 않을 것

- 원본 PDF와 원문 문장은 바꾸지 않는다.
- 노트북 실행 출력, 데이터 값, 차트는 바꾸지 않는다.
- 평가 결과 기록과 체크표의 과거 기록은 고치지 않는다. 필요하면 새 기록을 덧붙인다.
